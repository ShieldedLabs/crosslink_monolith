Zebra PoW/PoS instantiation of generic Crosslink 2

Three protocol quantities, two derived chain markers

Generic Crosslink 2 combines a best-chain protocol with a BFT protocol. Here blue PoW and red PoS/BFT show Zebra's instantiation. The blue chain itself is bc_best; the visualization then marks the other two quantities on that chain. Crosslinks let a block determine objective candidate(H). On each best-chain update, local history turns candidate(bc_best_tip) into fin. A derived candidate can move backward without the PoW best chain crossing fin. A best chain that actually forks below fin is a different, exceptional event.

Zebra Crosslink omits Stalled Mode, and with it the Book's bounded availability. Nothing lies between bc_best and fin, and nothing bounds how far the best chain runs ahead of fin.

See the full semantic and implementation analysis.

PoW / bc_best PoS / BFT LF(H) on PoS candidate(H) fin

Do not conflate two tests. The condition fin ⪯ candidate(bc_best_tip) can fail merely because the candidate lands behind fin. That does not mean the full best chain has rolled back a finalized block. A full-best-chain conflict means that fin and bc_best_tip are on different forks, with neither an ancestor of the other. That means this execution does not satisfy PoW Prefix Consistency at the chosen sigma, and it can strand miners on an unfinalizable branch. The candidate test alone does not detect it: the candidate of a conflicting tip can still be an ancestor of fin.

1. How candidate(H) crosses both chains

Arrows are committed references, not message flow. Newer blocks are at the top; parent links run downward.

2. All three values name PoW-chain points

The PoS chain helps compute the candidate, but bc_best_tip, candidate, and fin are all tips of PoW-chain prefixes.

FORK CHOICE

bc_best

“Which bc-valid chain has the highest score in this node's view?” It is available but not final. An application that keeps working through a finalization stall reads this chain, or a confirmation-depth prefix of it, and accepts an unbounded distance to fin.

CALCULATION

candidate(H)

“What finalization point does this particular PoW block and its linked ancestry imply?” On each bc_best_tip change, the node computes it for that best tip; every correct replay of the same H gets the same answer.

MEMORY

fin

“What is the furthest compatible candidate(bc_best_tip) this node has accepted across best-chain updates?” It depends on local update history, never moves backward, and is the view to which CL2's assured-finality guarantee applies.

Recommended client exposure condition: the Book recommends baking in a BFT checkpoint and withholding fin until that checkpoint precedes LF(bc_best_tip), its snapshot precedes fin, and fin's timestamp is sufficiently recent. This is sync-safety guidance, not a block-validity rule; Zebra does not implement it.

3. Benign case: candidate moves backward, but the best chain still contains fin

A shallow PoW reorg can expose an older BFT context. Its derived candidate can therefore be an ancestor of fin. That is not a rollback through finality: the complete new best chain still descends from fin.

Before: fin advances

bc_best_tip = P10 carries context S6, whose last final block S4 yields candidate = P5, so fin advances to P5.

After: candidate is older, not conflicting

The higher-work Q branch replaces only P8–P10, so bc_best_tip = Q10 still contains fin = P5. Its older BFT context yields candidate P4. Hold fin at P5.

Why this is benign: S3 carries [P5, P6, P7], so snapshot(S3) = P4. Its child S4 carries [P6, P7, P8], so snapshot(S4) = P5. The snapshots are linear, and both the old P chain and new Q chain contain fin = P5. Only the derived candidate moved backward.

candidate(bc_best_tip) descends from fin

On the best-chain update, advance fin to the candidate.

Candidate is an ancestor of fin

Hold fin. This can be benign when the complete bc_best still contains fin.

Candidate conflicts with fin

Hold fin and record a finalization safety hazard.

bc_best_tip itself conflicts with fin

Hold fin. The candidate test may only report "ancestor", so detect this separately; see §4.

4. Exceptional case: the raw PoW best chain forks below fin

This is not the benign case above. Because fin came from a previously sigma-confirmed prefix, a later bc_best that conflicts with it means this execution does not satisfy PoW Prefix Consistency at that confirmation depth. The abstract CL2 outcome below additionally assumes BFT Final Agreement and objective enforcement of the Linearity and Tail Confirmation validity rules.

This is the abstract CL2 safety path, not a claim about current Zebra. With BFT Final Agreement and objective enforcement of Linearity and Tail Confirmation, the BFT snapshot history cannot cross to C, so the finalized client view remains P5 while C is dominant. The current Zebra prototype does not implement those two validity rules and cannot claim this outcome from its present validation code.

Abstract CL2 response

Subject to the stated BFT assumptions, keep raw bc_best = C8; keep fin = P5; and prevent valid BFT snapshots from crossing forks. With Stalled Mode omitted, nothing restricts later C blocks: spends accumulate past fin for as long as C dominates, and would be rolled back if the best chain returns to P.

Current Zebra prototype response

Physical Crosslink finalization makes the committed branch canonical and makes the conflicting branch ineligible for activation. This locally enforces canonical_finalized_tip ⪯ canonical_tip — not the stronger property that a sigma-deep unfinalized prefix can never be displaced. That policy point and the successful database-commit boundary are not protocol fin; CL2 does not mandate this constraint, so adopting it is a Zebra decision that needs its own ZIP or ADR.

Design consequence: Zebra Crosslink omits Stalled Mode by design, so no consensus rule bounds ordinary activity along an unfinalizable branch. Removing Zebra's finalized-prefix behavior in order to imitate raw CL2 fork choice would remove the only local constraint on activating such a branch; keeping it costs the enforcing node's liveness while that branch dominates.

5. The fork-choice conclusion, with primary-source evidence

Following Crosslink 2 does not require Zebra to disobey the highest-score bc-valid-chain when that chain excludes fin. A finalized-prefix constraint is a separate design choice considered—but not adopted—by the TFL Book.

The construction defines best chain by highest score—accumulated work for PoW—in lines 245–260. It then tells honest block producers not to add BFT-derived constraints when choosing which bc-valid-chain to follow in lines 709–717.

The Questions chapter considers exactly the stronger rule: require bc_best to extend the snapshot of the latest final BFT block in the node's view. It says the change would break the current safety and liveness arguments (lines 17–26), and answers whether it should be made anyway:

“Probably not. I don’t know how to repair the safety and liveness arguments.”

— Questions about Crosslink, lines 44–52.

The Questions page analyzes the Last Final Snapshot rule on its own, and the potential-changes section notes that the argument against that rule was made for a protocol without Linearity. The fork-choice change belongs to the same discussion, part of which relies on the Finality Depth rule and Stalled Mode that this design omits; the Book does not revisit the change with Linearity in place. It declines the change because nothing useful can be said about snapshot(B) once BFT may be subverted. The per-block rule and the fork-choice constraint stay distinct: a block can satisfy the Last Final Snapshot rule with stale BFT context. Section 6 compares the constraint with sticky fork choice.

6. Sticky fork choice

A candidate rule for selecting bc_best that keeps the node's own fin on its best chain. It is temporal: the result depends on the chain the node is already on and on its current fin, not only on the chains in view.

Properties

These follow from the definitions of candidate and fin and the switch condition, and hold wherever protocol fin is computed.

Same as the finalized-prefix rule, with floor fin

Because the current chain always contains fin, pairwise switching selects the chain with the most work (then greatest tip hash) among chains containing fin. The eligible set shrinks each time fin advances.

Local invariant: fin ⪯ bc_best

A conflicting candidate cannot arise on the node's own chain, so the finalization safety hazard record is never written. The observable counterpart is a refused switch: a heavier chain in view that excludes fin.

Differs from raw fork choice only at a refused switch

fin was sigma-confirmed in this node's earlier best chain, so the raw rule would displace that prefix at exactly those moments. The node never switches to a chain with less work, and an advance of fin never causes a switch.

Finality pins only what work already selected

candidate(H) is an lca with prune_sigma(H), so fin moves only to blocks at or below prune_sigma(bc_best). While BFT is stalled or withholding, fin is frozen and selection above it is by work.

Relation to the Book's fork-choice discussion

The nearest relative of sticky fork choice in the Book is the fork-choice change it considers and declines (§5). The two differ in their floor.

The Book's fork-choice change: floor snapshot(B)

B is the newest final BFT block in the node's view. Its snapshot need not lie on any chain the node has selected, nor be sigma-confirmed in one.

Sticky fork choice: floor fin

fin advances only to candidate(bc_best), a block on the node's own best chain at or below prune_sigma(bc_best).

With Final Agreement and Linearity: a subset

fin ⪯ snapshot(B), because fin is at or below the snapshot of some final BFT block and those snapshots are linear. Sticky fork choice then refuses a subset of the chains the Book's change refuses. Without Linearity the two floors can conflict, and neither set contains the other.

With Last Final Snapshot as well: stale contexts

A chain whose last final BFT block extends the one that last advanced fin contains that block's snapshot, and therefore fin. Every refused chain carries an older BFT context.

The last column is the one that applies to the current Zebra prototype, once it computes protocol fin. The other two columns assume BFT Final Agreement and enforcement of the Linearity rule, as the abstract outcome in §4 does. The prototype enforces neither Linearity nor Last Final Snapshot.

What the Book says about changes of this kind: its honest-production instruction excludes BFT-derived information when choosing among bc-valid chains (§5). Its liveness analysis attributes its tractability to leaving fork choice unmodified, in contrast with Casper FFG, whose fork choice follows the justified checkpoint. Under sticky fork choice a node never switches to a lighter chain and never switches because fin advanced, but it can refuse a switch; the Book has no liveness argument for that. The Book declines its own change because nothing useful can be said about snapshot(B) once BFT may be subverted. A subverted BFT still cannot place fin off the node's best chain or above prune_sigma(bc_best), but by finalizing a sigma-confirmed prefix before a Prefix Consistency failure would displace it, it decides which branch the node keeps; the Book has no safety argument for that either.

Current Zebra: the rule needs protocol fin, which Zebra does not yet compute; the prototype's current finalized-branch collapse uses the BFT-decided marker as its floor instead. Zebra also commits the root of any best chain longer than MAX_BLOCK_REORG_HEIGHT (99), so on a Zebra node the effective floor is the higher of fin and that depth-committed block.

7. The shortest useful summary

bc_best is raw fork choice; candidate(H) is objective evidence; and fin is node-local monotone memory. An application either stops with fin during a finalization stall, or follows bc_best with no bound on how far it runs past fin. Sticky fork choice is a candidate rule that selects bc_best only among chains containing fin, ordered by work and then tip hash.
